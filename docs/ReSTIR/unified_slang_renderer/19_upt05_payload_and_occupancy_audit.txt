UPT-05 Payload, Live-State, and Occupancy Audit
===============================================

Date
----

2026-08-02

Trigger
-------

The 18 mechanical cleanup removed a conservative 801.563 MiB/frame of
explicit P0/D0 traffic at 2560 x 1440, but the user observed no meaningful
change in the hardware-counter pattern.  A separate Cyberpunk 2077 path-
tracing capture matched NVIDIA FullSample instead of rbdoom: ray dispatch was
RT-core-heavy, VRAM use was modest, and reads dominated the memory traffic.

That comparison rejects the idea that rbdoom's write-heavy behavior is an
ordinary consequence of path tracing.  The next shared low-level suspect is
compiled execution state: oversized RT payloads in P0 and a live-state-heavy
RayQuery megakernel in D0.

Disposition
-----------

The payload/live-state divergence is proven.  Its exact SASS register count,
local-memory spills, and causal share of frame time are not yet proven.  A new
full-frame traversal-isolation mode is built and deployed to obtain that proof.

Do not add temporal or spatial reuse until the new A/B is captured.  Runtime
feature switches cannot repair a statically oversized payload or reduce state
which the compiler must keep live across an inline traversal loop.

P0 primary ray payload
----------------------

Current shared UPT primary producer
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

pathtrace_primary_surface_producer.rt.hlsl declares a 336-byte, 84-dword
PathTraceSmokePayload.  It contains:

    hit distance, normals, tangent basis, UVs, barycentrics, vertex colors
    surface/material/instance/geometry/primitive identities
    shadow-ignore and debug state
    three detail-decal candidates across four payload arrays
    four liquid-pool candidates across six payload arrays

InitSmokePayload initializes this entire contract before every camera
TraceRay.  The decal and liquid arrays remain part of the static Vulkan
RayPayloadKHR type even when their runtime feature switches are disabled.
They therefore cannot be treated as zero-cost optional features.

The deployed P0 SPIR-V declares the complete 39-member payload type for the
ray-generation, any-hit, and closest-hit stages.  The host's stale
maxPayloadSize = 64 assignment does not shrink Vulkan SPIR-V; this old NVRHI
Vulkan path does not apply that D3D12 pipeline field to the shader payload ABI.

Early renderer payload
~~~~~~~~~~~~~~~~~~~~~~

The older pathtrace_smoke.rt.hlsl payload was already 176 bytes, or 44 dwords,
before detail-decal and liquid-pool state was added.  It carried full shaded
surface attributes rather than compact hit identity.  This proves the design
problem existed in the early basic DI/GI era and was later enlarged; optional
modern features are not required to explain its origin.

Reference payloads
~~~~~~~~~~~~~~~~~~

The local NVIDIA FullSample path-tracing RAB payload is 40 bytes, or 10
dwords:

    float3 throughput
    committed hit distance
    instance, geometry, and primitive identities
    front-face flag
    float2 barycentrics

It reconstructs geometry and material state after the hit from compact
identity and barycentrics.  Its ray-traced G-buffer payload is 28 bytes.

The exact size ratios are:

    rbdoom early core payload / NVIDIA PT payload       176 / 40 = 4.4x
    rbdoom current P0 payload / NVIDIA PT payload       336 / 40 = 8.4x

These ratios do not directly predict elapsed time.  They do establish a major
architecture-level divergence on the path shared by DI and GI.

D0 RayQuery live state
----------------------

Upt04InitialTraceWork is 168 bytes under the scalar layout:

    scalar candidate, replay, path, and PDF state        120 B
    Upt04TraceRequest                                     32 B
    Upt04BoundedTransportState                            16 B

Upt04IndirectHitTrialResult contains two such records and is 336 bytes.  The
unified D0 composition root also retains or copies the 176-byte primary
surface, direct work, continuation work, secondary-NEE work, reservoir state,
hit facts, decoded geometry/material state, and transport state while it
serially executes:

    primary NEE proposal and visibility
    BSDF continuation traversal
    hit geometry/material reconstruction
    endpoint candidate construction
    secondary NEE proposal and visibility
    unified reservoir streaming

The optimized Slang production SPIR-V is one inlined function with three
distinct OpRayQueryProceedKHR loops.  This is functionally a ray-query
megakernel even though its source is split into modules.  Source modularity
does not shorten the compiled live ranges.

RayQuery traversal shares SM execution and registers with surrounding shader
code.  A large live set can reduce resident warps and starve RT traversal; a
spill of shader-local values is backed by device memory and is a plausible
source of write-heavy VRAM counters.  This is an inference until Nsight reports
register/local-memory evidence or the isolation A/B separates it.

Full-frame traversal-isolation proof
------------------------------------

Shader proof 14 is a separate 8x8 compute module.  For every valid primary
receiver it performs:

    read header, world position, and geometric normal       48 B/pixel
    trace one opaque accept-first-hit inline ray
    write one committed-hit status uint                      4 B/pixel

It imports no light, material, reservoir, geometry-decode, initial-sampling,
or resolve module.  It uses only descriptor-set-0 bindings:

    t0 TLAS
    t1 primary receiver
    u4 uint result storage backed by the existing private page allocation
    128-byte push range for dimensions/counts

Compiled proof
~~~~~~~~~~~~~~

The verified runtime blob is 5,732 bytes.  Its SPIR-V contains:

    LocalSize 8 8 1
    exactly one OpRayQueryInitializeKHR
    exactly one static OpRayQueryProceedKHR loop
    ArrayStride 176 for the source receiver
    three 16-byte receiver-field loads, not a 176-byte struct load
    one 4-byte result store on the valid path
    no bindings 2, 3, 5, or bindless set 1

The Vulkan-only build and all UPT verification targets passed.  The rebuilt
executable and proof blob were deployed with matching source/destination
SHA-256 values:

    upt04_full_frame_traversal_probe.bin

Interpretation gate
-------------------

1. Proof 14 becomes RT-core-heavy and read-dominant.

   The TLAS and RayQuery mechanism can feed the RT cores.  Production D0's
   live state, material/light work, or spills are the governing cause.  Split
   D0 at explicit ray/work-queue boundaries before adding reuse.

2. Proof 14 remains near the reported 18-percent RT-core utilization.

   The production reservoir/material state is not sufficient to explain the
   low traversal occupancy.  Investigate TLAS traversal, ray coherence,
   scheduling, or a lower Vulkan/NVRHI issue before restructuring D0.

3. Proof 14 is RT-core-heavy but remains unexpectedly write-heavy.

   Inspect shader registers/thread and local-memory load/store counters for
   the 5.7-KiB module.  A compiler/backend or counter-scope issue is then more
   likely than the UPT work contract.

The proof ray starts at the primary hit and follows the geometric normal with
a long tMax.  It deliberately does not reproduce the production light or BSDF
distribution.  It answers whether the same live TLAS and Vulkan RayQuery path
can sustain traversal when the surrounding state is removed; it is not an
image-quality or equal-ray-distribution benchmark.

Accepted runtime result
-----------------------

The user captured proof mode 14 in Nsight.  Traversal rose to nearly maximum
RT-core utilization toward the end of the marker and appeared constrained by
VRAM reads rather than writes.  This accepts interpretation case 1:

    the live TLAS is capable of feeding the RT cores;
    Vulkan inline RayQuery is not intrinsically limited to the production
        shader's roughly 18-percent RT-core utilization;
    descriptor-set mapping and the NVRHI RayQuery path are not the shared
        low-utilization cause;
    production D0's surrounding live state and/or shading work is responsible
        for starving traversal and producing the pathological write pressure.

Read pressure at high traversal utilization is not the failure seen in the
production capture.  Acceleration-structure and geometry traversal naturally
consume reads.  The important inversion is that the minimal proof drives the
RT cores while production D0 is write-heavy with the RT cores mostly idle.

One discriminator remains before admitting queue buffers.  Capture the
existing production ray-generation backend with the same family, scene, and
camera.  It retains the same source-level sampling/shading sequence but moves
traversal behind TraceRay with a 32-byte hit payload:

    r_pathTracingUnifiedPtEnable 0
    r_pathTracingUnifiedPtBackend 1
    r_pathTracingUnifiedPtFamily 0
    r_pathTracingUnifiedPtDiagnostics 0
    r_pathTracingUnifiedPtResolve 0
    r_pathTracingUnifiedPtProofStage 9
    r_pathTracingUnifiedPtShaderProof 6
    r_pathTracingUnifiedPtFixedSampleIndex -1
    r_pathTracingUnifiedPtEnable 1

Select only:

    UPT.D0 Initial RayGen DispatchRays FullFrame

If raygen restores high RT utilization and removes the write ceiling, prefer
the existing compact-payload raygen backend and then reduce its remaining live
state before adding reuse.  If raygen retains the production RayQuery counter
pattern, admit an explicit D0 split at the continuation-hit boundary; do not
add generic queues without that result.

Likely remediation boundary if case 1 passes
--------------------------------------------

P0 must get a UPT-owned compact hit payload containing only hit distance,
instance/geometry/primitive identity, barycentrics, and front-face state, with
surface/material reconstruction after TraceRay.  Decal and liquid collection
must attach through explicit optional passes or specialized pipelines rather
than enlarging the baseline payload.

D0 must cease being one three-query live-state kernel.  Candidate/reservoir
state must be compact at each pass boundary, and separate traversal/shading
stages must justify each queue and buffer in the GPU work ledger.  This is not
authorization to add generic queues speculatively; the proof result selects
the next design.

RTX Remix primary-visibility comparison
---------------------------------------

The user supplied an NvRemixBridge GPU Trace as a fully ray-traced primary-
visibility comparison.  The frame-level selection reports an approximately
85.73-percent RT-core ray-tracing input dependency.  It must not be compared to
UPT P0 at whole-frame scope because the capture also contains direct and
indirect integration work.

The local Remix source confirms that its path-tracer G-buffer produces primary
visibility with hardware rays, not rasterization.  It exposes three primary
backends:

    compute RayQuery
    ray-generation shader containing RayQuery
    ray-generation shader using TraceRay

On NVIDIA the automatic preset selects compute RayQuery for G-buffer primary
rays and direct integration, then TraceRay for indirect integration.  In the
supplied capture the single visible 5.75-ms vkCmdTraceRaysKHR is therefore most
likely indirect integration rather than primary visibility.  The exact P0
comparison scope is the nested profile region:

    Gbuffer Raytracing
        Primary Rays

With the automatic NVIDIA preset this region is a 16x8 compute dispatch.  Use
its RT-core utilization, VRAM reads/writes, live registers, local-memory
loads/stores, and duration; do not use the aggregate 33.9-ms frame or assume
the largest TraceRays event is primary.

The current Remix source contains a particularly relevant design correction.
Its hot primary pass defers uncommon work to explicit follow-up passes:

    PSR Prepare
    Unordered Decal Prepare

The source states that this keeps PSR sampling and unordered decal blending
out of the common Primary Rays variants and reduces register pressure.  This
is the inverse of rbdoom P0, where decal and liquid candidate arrays are
members of the 336-byte static ray payload for every primary ray regardless of
runtime use.

Remix also packs its RayQuery GeometryResolverState aggressively: half-
precision direction, attenuation, cone radius and accumulated rotation, plus
bit-packed flags.  Its RayQuery primary path has no TraceRay payload at all;
material resolution uses compact local state and writes explicit G-buffer
outputs.  This reference does not authorize copying Remix code or layouts.  It
does validate the required rbdoom design constraints:

    keep the common primary traversal state compact;
    keep optional/rare material features out of its static live contract;
    attach PSR/decal/liquid work at separately measured boundaries;
    compare the actual primary profile region, not an entire path-traced frame.

UPT-only compact-primary A/B implementation
--------------------------------------------

The first P0 isolation change is implemented as a separately compiled Vulkan
RT library.  It is selected only when UPT is the sole primary-surface consumer
and the experiment cvar is enabled:

    r_pathTracingUnifiedPtLeanPrimary 0  existing shared P0, 336-byte payload
    r_pathTracingUnifiedPtLeanPrimary 1  UPT lean P0, 172-byte payload (default)

The lean variant removes the three-entry detail-decal bin and four-entry liquid
candidate set from the static TraceRay payload.  SPIR-V inspection confirms its
RayPayloadKHR type has exactly the original 24 base members through debugFlags;
the compiled library is 586,440 bytes versus 1,073,604 bytes for the unchanged
shared variant.  It still writes the same 176-byte PathTracePrimarySurfaceRecord
and retains ordinary opaque, alpha-tested, and filter-decal receiver behavior.
Liquid modifier cards and detail/additive decal cards pass through to their
base receiver in this test; their appearance is intentionally not part of this
payload-cost experiment.

The Nsight ranges identify the selected binary without changing any other UPT
work:

    UPT.P0 SharedPrimary DispatchRays
    UPT.P0 LeanPrimary DispatchRays

Test with the normal full-sample UPT configuration at the same camera and
resolution.  Toggle only r_pathTracingUnifiedPtLeanPrimary between 0 and 1,
allow the lazily selected pipeline to build once, then capture a steady frame.
Compare P0 duration, RT-core utilization, VRAM read/write throughput, registers,
local-memory traffic, and occupancy.  Also compare D0 duration to catch a
downstream receiver-contract change; its inputs and binary must otherwise be
identical.  A meaningful P0 gain with stable D0 validates the payload/live-state
cause.  No gain rejects payload size alone and points the next split at material
reconstruction inside P0 rather than optional candidate transport.

Compact-payload runtime result and L2 follow-up
-----------------------------------------------

The first comparison capture used lean primary and the second used the normal
shared primary.  The lean payload visibly reduced VRAM traffic and increased
RT-core use, but neither reached the reference utilization shape.  The user
also identified persistent near-90-percent L2 utilization across rbdoom's hot
work, unlike the comparison renderers.  Therefore optional payload state was a
real cost but not the underlying cache-working-set problem.

Two exact source/SPIR-V findings explain the remaining L2 pressure:

* P0 any-hit loaded the full 112-byte material and interpolated UVs from three
  112-byte vertices before its final test proved the common triangle was not
  alpha-tested.  This ran for ordinary opaque candidate hits because primary
  TraceRay uses RAY_FLAG_NONE, and closest-hit fetched the vertex attributes
  again for the committed hit.
* Production D0 performs one OpLoad of the complete 176-byte
  Upt04PrimarySurfaceRecord before extracting fields.  At 2560x1440, one full
  write or read is 648,806,400 bytes (about 619 MiB); P0 write plus D0 read is
  about 1.30 GB per frame before geometry, lights, textures, or the reservoir.

The immediate follow-up keeps all hit rules but resolves material index, flags,
and triangle class once per any-hit invocation.  Opaque candidates now return
before full material loading, UV interpolation, texture work, or stochastic
coverage.  Lean liquid/detail-card pass-through uses the existing static
material classification flags instead of loading the feature record and full
material for every candidate.  SPIR-V confirms the common flags probe is a
scalar uint load at material member 8; full material loads remain only behind
special coverage branches.

This is the next isolated runtime test.  Compare a new lean-primary capture to
the saved lean-primary capture at the same camera.  A P0/L2 improvement proves
unconditional any-hit reconstruction was another common-path defect.  The
remaining already-proven structural target is a UPT-owned compact receiver:
production D0 only consumes primary validity, position, normals, view direction,
roughness, base color, and F0, so it must not retain the legacy 176-byte history
record merely for compatibility with unrelated temporal/material consumers.

Opaque fast-path runtime result and synchronization audit
---------------------------------------------------------

The common opaque any-hit fast path shortened P0 and reduced its traffic, but
the next capture showed the saved interval as a visible P0-to-D0 gap while D0
and the remainder of the frame stayed heavily loaded.  This rejects opaque
any-hit reconstruction as the dominant limiter and confirms that making one
producer locally cheaper cannot repair the downstream working set.

The gap also exposed stale shared-producer synchronization.  UPT-only sets the
primary producer's RR publication bit to zero, so it writes none of the motion
or RR guide images.  Nevertheless the host requested UAV state before P0 and
UAV-to-UAV barriers after P0 for ten such images.  This NVRHI version maps UAV
state to ALL_COMMANDS plus shader read/write access.  UPT-only now omits those
explicit image requests.  It also omits the redundant post-P0 receiver UAV
barrier because D0's existing UAV-to-SRV transition is the actual required
P0-write to D0-read dependency.  Clean DI retains the original barriers.

This is synchronization cleanup, not the structural performance claim.  The
shared P0 binding set still contains unused guide UAVs and NVRHI automatically
tracks bound resources.  A future UPT-owned P0 layout may remove those bindings,
but only after the compact receiver A/B measures the dominant traffic change.

Frozen UPT current-frame receiver contract
------------------------------------------

The hot P0-to-D0 record is 48 bytes, expressed as three uint4 words:

    positionAndHeader
        xyz: full-precision world position bit patterns
        w: packed receiver version and valid bit

    directionsAndRoughness
        x: 2x16-bit octahedral geometric normal
        y: 2x16-bit octahedral shading normal
        z: 2x16-bit octahedral view direction
        w: fp16 roughness; upper half reserved

    material
        fp16 baseColor.rgb and specularF0.rgb
        final uint reserved

The producer writes exactly one record.  Compact mode does not also publish the
176-byte history record.  D0 expands the 48-byte record to its existing logical
surface value after the single buffer load, so material-provider and ReSTIR
code remain independent from the storage ABI.

The exclusions are intentional:

* previous position, motion, material identity, instance/primitive identity,
  emissive, alpha cutoff, opacity, and surface class are not read by the
  admitted current initial sampler;
* temporal/spatial validation and reconnection identity must use an optional
  sidecar later rather than enlarge every current-frame D0 load;
* PSR, decal/liquid collections, and special shading remain separate producer
  or material-provider responsibilities;
* three-bounce continuation and aggressive Russian roulette are not impaired:
  current continuation already needs only position, directions, roughness,
  base color, and F0.  Per-bounce state stays in the bounded transport contract.

At 2560x1440, the record changes one full-frame write or load from 648,806,400
bytes (about 619 MiB) to 176,947,200 bytes (about 169 MiB), a 72.7-percent
reduction.  P0 write plus D0 read falls from about 1.30 GB to 353,894,400 bytes
before traversal, lights, geometry, textures, and reservoir traffic.

Runtime A/B:

    r_pathTracingUnifiedPtCompactReceiver 0  legacy 176-byte receiver
    r_pathTracingUnifiedPtCompactReceiver 1  UPT-owned 48-byte receiver (default)

It applies only to UPT-only Vulkan execution, diagnostics off, and production
shader-proof modes 1 through 6.  Diagnostic and live-TLAS proof variants keep
the legacy ABI.  The pipeline log prints receiver=compact48 or receiver=legacy176,
and the compact P0 marker is:

    UPT.P0 LeanPrimary Compact48 DispatchRays

SPIR-V proof for the direct-only compact consumer records ArrayStride 48 and
loads Upt04PackedPrimarySurfaceRecord.  The retained A/B blob records
ArrayStride 176 and loads Upt04PrimarySurfaceRecord.  Both RayQuery and raygen,
and unified/direct-only/indirect-only family variants, are separately compiled
and Vulkan-validated.

Experimental 32-byte receiver A/B
---------------------------------

Mode 2 tests whether the remaining 16 bytes per pixel cross a cache or memory-
traffic threshold.  It keeps full-precision primary hit distance, packs the
geometric normal, shading normal, and surface-to-camera direction as octahedral
2x16-bit values, and packs base color, roughness, and F0 as fp16 values.  D0
reconstructs world position as:

    primaryCameraOrigin - viewDirection * hitDistance

The camera origin reuses three otherwise unconsumed UPT-04 push-constant words;
the push-constant ABI remains 128 bytes and no matrix or new constant buffer is
introduced.  Mode 1 remains the proven 48-byte world-position receiver, so any
precision or performance regression has an immediate control.

At 2560x1440, one compact32 full-frame access is 117,964,800 bytes (112.5 MiB).
P0 write plus D0 read is 235,929,600 bytes (225 MiB), saving 117,964,800 logical
bytes per frame versus compact48.  These figures describe the shader-visible
record footprint; Nsight must determine physical L2/VRAM traffic and timing.

    r_pathTracingUnifiedPtCompactReceiver 0  legacy 176-byte receiver
    r_pathTracingUnifiedPtCompactReceiver 1  compact48 control/default
    r_pathTracingUnifiedPtCompactReceiver 2  experimental compact32

The compact32 pipeline log prints receiver=compact32 and P0 uses marker:

    UPT.P0 LeanPrimary Compact32 DispatchRays

Emitted SPIR-V proves ArrayStride 32 and one structured record load.  Six
Vulkan runtime variants cover RayQuery/raygen and unified/direct-only/indirect-
only families.  For this first fair A/B, compact48 and compact32 buffers are
both allocated at resize but only the selected buffer is written and read.
Thus mode switching does not change allocation pressure, while the inactive
buffer contributes no per-frame shader traffic.  Remove the losing allocation
after measurement rather than hiding allocation differences inside this test.

Deferred PCIe incoming-BAR hitch investigation
-----------------------------------------------

After compact32 made P0/D0 traffic and RT-core utilization resemble the
reference renderers, D0 still exhibited two repeatable performance states with
an approximately eight-FPS difference.  Both the direct-only and indirect-only
families can enter the slow state, so it is not specific to the unified
shader's serial direct/continuation/secondary-visibility sequence.  The user
observed a stronger correlation: fast frames show no PCIe Incoming BAR Access,
while slow/hitching frames show incoming BAR activity overlapping D0.

Treat this as a deferred cross-cutting upload/residency issue, not evidence
against compact32 and not a reason to continue modifying D0 shading.  Relevant
future suspects are the many per-frame scene-buffer uploads and the old NVRHI
Vulkan upload manager, whose shared UploadChunk usage includes acceleration-
structure-input and shader-binding-table flags.  CPU preparation of the next
frame may therefore overlap current-frame D0 through mapped upload or ReBAR
memory and contend with the L2 cache used by RayQuery traversal.  This remains
a hypothesis until the selected Vulkan memory type and concurrent upload bytes
are measured.

Required future proof, as one isolated task:

* report the actual Vulkan memory-type index and property flags for UploadChunk;
* report per-frame upload bytes grouped by destination buffer;
* freeze the scene, publish one accepted upload frame, then suppress subsequent
  scene uploads without reallocating or rebinding resources;
* compare D0 duration, PCIe Incoming BAR Access, L2 behavior, and the two FPS
  states with and without those uploads.

If the slow state disappears, pursue generation-gated uploads and dedicated
system-memory staging.  Do not use shader feature removal or additional D0
packing as a substitute for that proof.

Experimental 48-byte geometry replay sidecar
----------------------------------------------

The first post-receiver experiment applies the same storage-versus-logical-
contract separation to D0 geometry replay.  The authoritative scene and TLAS
buffers remain the existing 112-byte PathTraceSmokeVertex ABI.  When enabled,
a UPT-only compute pass reads each live static, dynamic, rigid, and skinned
vertex once and writes a 48-byte sidecar immediately before D0.  D0 binds the
sidecars at the existing vertex descriptor slots; no new set-0 descriptors and
no CPU upload path are added.

The 48-byte record keeps fp32 position, oct16 normal and tangent, tangent-frame
handedness, fp16 primary/normal texture coordinates, and fp16 vertex color and
additive color.  D0 expands it to the existing logical Upt04SmokeVertex before
material evaluation.  The scene ABI, BLAS/TLAS input, material-provider API,
and reservoir ABI are unchanged.

Runtime A/B (RayQuery production only):

    r_pathTracingUnifiedPtCompactReceiver 2
    r_pathTracingUnifiedPtCompactGeometry 0  legacy112 replay
    r_pathTracingUnifiedPtCompactGeometry 1  GPU-packed compact48 replay

Mode 1 is admitted only with Vulkan RayQuery, diagnostics off, shader proofs
1 through 6, and compact receiver mode 2.  The pipeline log prints
geometry=compact48 or geometry=legacy112.  Nsight separates the new cost as:

    UPT.G0 CompactGeometry48 Dispatch
    UPT.D0 Initial RayQuery Dispatch FullFrame

The experiment must be judged on G0+D0 combined time as well as D0 alone.
Capture visual parity, G0 duration, D0 duration, combined duration, L2 and VRAM
throughput, RTCORE dependency, and the incoming-BAR state.  Packing every frame
is deliberate for this first correctness-safe A/B; generation-gating static
and rigid repacks is a later optimization only if the storage reduction wins.

Emitted SPIR-V proves ArrayStride 48 for the compact D0 vertex buffers and has
no 112-byte smoke-vertex storage buffer in that D0 variant.  The separate G0
shader proves one 112-byte source load and one 48-byte destination record per
eligible vertex pool element.  The retained legacy D0 variants remain the
rollback/control.

Runtime acceptance: the compact48 geometry capture reduced D0 to about 0.94 ms
in the user's test, reduced sustained cache load, and removed most of the
violent frame-time fluctuations.  G0 remained visually small relative to D0.
This is evidence that the wide replay ABI crossed a cache/contention threshold,
not merely that it added a small linear bandwidth cost.

Experimental 64-byte current-light sidecar
-------------------------------------------

The next isolated experiment keeps the manager-owned 112-byte RLU current
payload authoritative and GPU-packs only the current records consumed by D0.
It is gated on the accepted compact32 receiver plus compact48 geometry lane, so
its rollback changes only light storage.

The 64-byte record keeps full-precision position, analytic radius, emissive
area, and Doom influence radius; oct16 emissive normal; fp16 radiance and
luminance; and the complete source/material/instance/primitive/hash identity
set.  The unused sourcePdf, previousIndex, padding, and unused Doom parameter
components are absent.  Positive sourceWeight is represented as an admission
bit during packing because D0 never consumes its magnitude.

Runtime A/B:

    r_pathTracingUnifiedPtCompactReceiver 2
    r_pathTracingUnifiedPtCompactGeometry 1
    r_pathTracingUnifiedPtCompactLights 0  manager-owned legacy112 records
    r_pathTracingUnifiedPtCompactLights 1  GPU-packed compact64 sidecar

The pipeline log prints lights=compact64 or lights=legacy112.  Nsight exposes:

    UPT.L0 CompactLight64 Dispatch
    UPT.D0 Initial RayQuery Dispatch FullFrame

Judge L0+D0 combined time, image parity, light cutoffs/intensity, L2/VRAM
throughput, RTCORE dependency, and frame stability.  The pack executes each
frame for the first A/B; generation-gating it is a later optimization if the
storage reduction wins.

Emitted SPIR-V proves ArrayStride 64 and compact-light loads in D0 with no
112-byte unified-light storage buffer.  The separate L0 pack shader is the only
module that loads the authoritative 112-byte light record.
