UPT-23: Frozen scene and static-flat isolation
================================================

Purpose
-------

Separate four costs that normal gameplay and a whole-frame Nsight capture mix
together:

    per-frame scene/universe publication;
    BLAS/TLAS build or update;
    GPU identity/geometry route lookup;
    actual traversal, reservoir work and material shading.

This is a diagnostic lane. It does not change production UPT sampling,
temporal/spatial reuse, reservoir storage, ray ceilings or defaults.

Control
-------

    r_pathTracingUnifiedPtFrozenScene 0
        Normal scene construction and production shaders.

    r_pathTracingUnifiedPtFrozenScene 1
        Capture the next complete production scene. After a successful commit,
        the host changes the cvar to 2.

    r_pathTracingUnifiedPtFrozenScene 2
        Replay the committed production scene package. Scene construction exits
        before particle capture and all geometry/material/light universe,
        upload and acceleration work. Camera and UPT output/history remain live.
        Requesting 2 without a snapshot admits one capture frame.

    r_pathTracingUnifiedPtFrozenScene 3
        Capture and replay the current monolithic static publication. The
        capture TLAS contains only static BLAS instance zero. Dynamic BLAS,
        static-bucket, rigid and skinned TLAS instances are omitted. D0/T0 use
        direct primitive-indexed geometry, fixed dense analytic lights and
        identity previous/current mapping.

    r_pathTracingUnifiedPtFrozenScene 4
        Capture and replay the complete production geometry/TLAS package, but
        use analytic-only light proposals, identity current/history mapping,
        and no emissive lookup. This is the light-flat-only factorial corner.

    r_pathTracingUnifiedPtFrozenScene 5
        Capture and replay the monolithic static-only TLAS, but retain the full
        production emissive distribution, emissive lookup, previous/current
        remapping and D0 previous-best closure. This is the geometry-flat-only
        factorial corner.

Light-flat proposal and lookup boundary
---------------------------------------

Modes 3 and 4 are analytic-NEE-only. Emissive NEE range/count, distribution and
lookup metadata are zero. Emissive material self-emission may still be observed
when a continuation hits an emissive surface, but reverse-NEE MIS uses zero NEE
PDF and performs no geometry-to-emissive hash search. D0 previous-best replay is
also statically absent rather than merely disabled through its runtime flag.

The shader still loads dense light records and triangle material records; those
are input data for lighting and shading, not persistent-identity searches.
Mode 3 statically removes both mechanism groups:

    gUpt07PreviousToCurrentLights;
    gUpt04EmissiveLookup;
    dynamic geometry arrays;
    rigid route arrays;
    skinned route arrays;
    static-bucket route dispatch.

Both OpenPBR and constant-gray Lambert specializations exist. Select Lambert
with r_pathTracingUnifiedPtLambertDiagnostic 1. No runtime shading branch is
used to create that comparison.

Build proof, 2026-08-10
-----------------------

The prescribed Vulkan release build passes and links RBDoom3BFG.exe. Runtime
artifacts include six D0 and twelve T0 frozen-factor variants: both-flat,
light-flat-only and geometry-flat-only, each with OpenPBR/Lambert and T0
duplication off/on. No DX12 shader was added or compiled.

SPIR-V disassembly proves the two missing corners are orthogonal. Light-flat
D0/T0 retain dynamic, rigid and skinned geometry symbols but contain zero
emissive-lookup or previous/current-remap symbols. Geometry-flat D0/T0 contain
zero dynamic, rigid or skinned geometry symbols but retain emissive lookup and
the appropriate D0/T0 remap binding. Every D0 variant retains three RayQuery
proceed sites and every T0 variant retains four. No corner lowers the
established ray ceiling.

Runtime matrix
--------------

Use one fixed camera and keep the ordinary UPT family, temporal, spatial,
duplication and resolution controls identical between rows. Use
r_pathTracingUnifiedPtTemporalGpuTiming 1 for dispatch-only T0 measurements;
use Nsight markers for D0 and whole-frame/scene-build confirmation.

    A. frozenScene 0: live production baseline.
    B. frozenScene 1 -> 2: production geometry and full light machinery.
    C. frozenScene 4: production geometry and analytic-only light machinery.
    D. frozenScene 5: static geometry and full light machinery.
    E. frozenScene 3: static geometry and analytic-only light machinery.

Keep Lambert fixed at zero for A--E. A separate E/OpenPBR versus E/Lambert
comparison remains available for material-cost isolation. Toggle
r_pathTracingUnifiedPtTemporalGpuTiming to zero and back to one before every
row so each row arms a new 64-sample batch.

Required log evidence:

    frozen scene captured mode=2, 3, 4 or 5;
    frozen scene replay ... sceneBuild=skipped uploads=0 blas=0 tlas=0;
    frozen factor shader mode=N effective=1 geometry=... lights=...;
    D0/T0 pipeline shading=frozen-factor-openpbr.

First field result, 2026-08-10
------------------------------

At 2560x1440 the recorded live T0 batch was 18.872 ms median. The user observed
that frozen production replay reduced the representative cost by roughly 4 ms,
while the bundled static/analytic mode reduced it to roughly 6 ms. Therefore
scene/acceleration interference is material, but the larger remaining reduction
is inside the geometry/light bundle. Exact re-armed batches for modes 2--5 are
the next acceptance evidence.

Interpretation
--------------

    A -> B:
        scene/universe publication or acceleration events contaminated the
        measured frame.

    B -> C:
        full emissive proposal, lookup and identity-remap machinery is material
        while production geometry/TLAS remains fixed.

    B -> D:
        production geometry routing or TLAS content is material while the full
        light machinery remains fixed.

    C/D -> E interaction:
        the two mechanism groups amplify each other; report the interaction
        rather than assigning the combined saving to one side.

    E remains slow:
        traversal, unified reservoir/shift work, code footprint or occupancy
        remains the bottleneck.

    E OpenPBR -> E Lambert improvement:
        material evaluation owns the difference.

    E OpenPBR and Lambert similar:
        OpenPBR is excluded for this frozen workload.

Limitations and safety
----------------------

The camera is live; freeze player position manually for matched timing. Modes 3
and 5 capture the current static publication rather than constructing a new
spatial AABB clip, so capture immediately in the intended portal/room after a
clean map load for the narrowest chunk. Moving doors, actors, rigid props and
skinned meshes are intentionally absent. Mode 5 deliberately retains the full
light universe, so dynamic emitters whose geometry is absent can produce an
invalid image; mode 5 is timing evidence only. Changing maps invalidates the
snapshot through the normal resource reset. Returning the cvar to zero resumes
normal scene publication and invalidates UPT history without a full reservoir
clear.

Exact factorial runtime timings remain open; mode 5 has no image-acceptance
requirement beyond remaining stable enough to collect its timing batch.

Expanded field result and replay correction, 2026-08-10
--------------------------------------------------------

The rigid/skinned narrow-load implementation in UPT-24 produced no visible
performance difference. A second Doom view then exposed a much larger state
effect: live mode 0 ran at about 18 FPS, frozen production modes 1/2 at about
44 FPS, and frozen static mode 3 at about 56 FPS. More importantly, stepping
backward from 3 through 2 and 1 to 0 left mode 0 substantially faster at the
same camera. That hysteresis rejects a purely per-hit route-decode explanation.
The leading boundary is now persistent scene/acceleration planning state or
work allowed to converge while frozen replay bypasses its producers.

The host also contained a concrete frozen-mode state-machine bug. Successful
captures for every request >=3 were recorded as captured mode 3. Modes 4 and 5
therefore failed their replay-mode match on the following frame and rebuilt the
scene continuously. Their previous timing results are invalid. Captured modes
4 and 5 now preserve their requested identities and can enter the same early-
return replay path as modes 2 and 3.

Returning from any frozen mode to mode 0 now emits eight consecutive
`frozen release audit` records without requiring another cvar. Each record
includes full scene-function time, the earlier pre-BVH scene timer, capture,
material, emissive, buffer create/upload, BVH plan and BLAS/TLAS submission
times; geometry/TLAS counts; and rigid-route, rigid-TLAS, BVH and acceleration
async cache/queue state. This deliberately measures beyond the old `sceneMs`
cutoff, which occurs before BVH frame planning and could not explain the
observed mode-0 convergence.

Next runtime evidence
---------------------

At the fixed 18 FPS view, perform one clean mode-0 sample, then 1 -> 2, then 3,
then 2 (which captures through mode 1), then 0. Preserve the eight release-audit
lines after the final zero. A falling fullSceneMs or changing async cached/
queued state identifies a CPU publication/planning convergence effect. Stable
CPU timings with a faster mode-0 GPU frame instead implicate the submitted
TLAS/BLAS content or GPU residency/cache state. Do not start the common-route
architecture change until this split is resolved.
