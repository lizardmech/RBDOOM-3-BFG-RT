GEO-11 - Enforce AS budgets, in-flight lifetimes, and safe compaction
====================================================================

GOAL
----
Make BLAS/TLAS work admission, scratch use, result-buffer lifetime, retirement,
and optional compaction explicit and safe under real frame overlap.

PRECONDITIONS
-------------
- GEO-10 static buckets are correct in compare mode.
- This ticket must not change geometry identity or shading semantics.

FILES TO AUDIT FIRST
--------------------
  neo/renderer/NVRHI/PathTraceAcceleration.cpp/.h
  neo/renderer/NVRHI/PathTraceAccelerationPlan.cpp/.h
  neo/renderer/NVRHI/PathTraceCpuWork.cpp/.h
  neo/renderer/NVRHI/PathTraceSmokeSceneBuild.cpp
  neo/renderer/NVRHI/PathTraceSceneInputs.h

STEPS
-----
1. Trace command-list submission, queue, frame slots, fences, TLAS instance
   buffer lifetime, AS result lifetime, scratch reuse, and deferred destruction.
2. Define build admission budgets for operation count and scratch/result bytes.
   Separate new builds, updates, periodic rebuilds, and compaction copies.
3. Prioritize correctness-critical active work; defer eligible background work
   with explicit reason/age counters. Never omit a live object silently.
4. Prove TLAS consumes only BLAS handles whose build/copy completed and whose
   buffers remain alive through the last referencing submission.
5. Prove TLAS result and instance buffers are double/triple-buffered or fenced
   against in-flight overwrite. Include frame-slot/generation diagnostics.
6. Audit NVRHI/Vulkan support for compacted-size query and AS copy. If supported,
   implement compaction as build -> query -> allocate -> copy -> completion ->
   handle publish -> old-handle retirement. If unsupported, record the result
   and leave compaction disabled; do not emulate unsafe swapping.
7. Stress spawn/despawn, portal churn, map restart, buffer growth, and forced low
   budgets. Deferred work must converge and failures must remain recoverable.
8. Re-run comm1 generation tuple, crowded skinned updates, and lifecycle removal.
9. Capture median/p90/max build/update/TLAS times, budget use, deferred ages,
   scratch high-water mark, result bytes, and compaction savings.

VALIDATION
----------
- Zero stale AS handle, in-flight overwrite, premature retirement, or silent
  omission counters under normal and forced-low-budget tests.
- Deferred active work has a visible safe fallback or preserves last valid AS.
- Compacted handle is never exposed before copy completion.

DONE WHEN
---------
AS work and memory have proved admission/lifetime contracts; compaction is
either safely implemented with measured benefit or explicitly rejected by the
current backend capability audit.

SLICE-4 ADMISSION PLANNER CONTRACT
----------------------------------
The first Slice-4 implementation is deliberately CPU-only. One deterministic
planner now classifies work as new build, update, periodic rebuild, or future
compaction copy; orders critical-active, active, then background work; and
orders older deferred work first within each priority. It independently
enforces an operation cap and an authoritative allocated-result-byte cap.
Every rejected request records one exact reason:

  operation budget
  result-byte budget
  result bytes unknown while a byte budget is active

Zero is the explicit unlimited value for each budget. Scratch is not estimated
or represented because the active NVRHI interface does not expose an exact
per-build scratch requirement. Unknown result sizes are admitted only when the
result-byte budget is unlimited.

The CPU planning harness proves stable request-indexed decisions, exact
priority/age order, work-kind counts, deferral-reason counts, admitted-byte
totals, and unlimited behavior.

Runtime integration remains provider-by-provider. A counter must not be added
directly to the existing paths:

  - canonical rigid replacement already retains its prior complete BLAS and is
    the first safe integration target;
  - static buckets currently retire an old BLAS before replacement admission;
  - legacy rigid currently replaces vertex/index buffers before replacement
    BLAS admission.

Static-bucket and legacy-rigid paths must first retain one complete old
buffer/BLAS publication until the replacement is admitted and built. Main
dynamic scene work remains correctness-critical and outside the auxiliary
provider budget until it has an explicit safe fallback.

SLICE-4 CANONICAL-RIGID INTEGRATION
-----------------------------------
Canonical rigid is the first runtime consumer of the common planner. Its
existing operation CVar remains authoritative:

  r_pathTracingGeometryCanonicalRigidBlasBuildsPerFrame

The result-byte cap is independently controlled in KiB:

  r_pathTracingGeometryCanonicalRigidBlasResultBudgetKB

The default is 0, meaning unlimited, so production behavior does not acquire
result-requirement queries or a new byte cap by default. With a nonzero cap,
each candidate BLAS is queried through
`getAccelStructMemoryRequirements` before build submission. A zero result is
unknown and defers explicitly. A byte- or operation-deferred replacement
keeps the prior complete BLAS published; a new mesh remains on the existing
legacy route until its canonical BLAS is ready.

All requested canonical meshes are active work. Previously deferred records
are ordered oldest-first. A cap smaller than one BLAS cannot starve that mesh:
when the frame has admitted no result bytes, one oversized active result may
be admitted and is reported by both count and bytes. Remaining work stays
deferred. This makes forced-low-budget runs converge.

The expanded canonical BLAS line reports:

  admission(deferOp/deferBytes/deferUnknown/deferAlloc/query/fail/
            bytes/oversized/oversizedBytes/maxAge)

STATIC-BUCKET FAIL-RETAINED REPLACEMENT
---------------------------------------
The prerequisite audit found two coupled defects:

  - a changed bucket retired its prior BLAS before the build-count gate and
    replacement allocation;
  - compatibility required `geometryDescCount == 1`, although the accepted
    GEO-10 layout intentionally emits one geometry per bucket surface.

The latter made every multi-geometry bucket appear incompatible on every
frame, causing needless rebuild/retirement churn and explaining the observed
high bucket-BLAS overhead.

Static bucket replacement now always creates and records a distinct candidate,
submits its build, and only then retires and replaces the prior published
handle. Build-count deferral or allocation failure leaves the prior complete
record untouched. Force rebuild also uses build-then-swap rather than mutating
an in-flight published BLAS.

Ready/TLAS/publication checks now require the BLAS input signature to match the
current pack, bucket range, and current vertex/index buffer identities. A
retained old BLAS is therefore lifetime-safe but cannot be published against
new decode buffers; the bucket route fails closed to the monolithic fallback
until every active replacement is exact.

Compatibility now compares the recorded geometry count with the exact current
geometry-plan count. Diagnostics add `retainedReplacement` to distinguish safe
old handles from ready current handles and correct the stale geometry-layout
label.

STATIC-BUCKET RESULT-BYTE ADMISSION
-----------------------------------
Static buckets now consume the common deterministic admission planner. The
existing build-limit CVar remains the operation cap:

  r_pathTracingGeometryStaticBucketBlasBuildLimit

The independent result-byte cap is:

  r_pathTracingGeometryStaticBucketBlasResultBudgetKB

Its default is 0, meaning unlimited and therefore no admission-time result
requirement queries. With a nonzero cap, each candidate handle is queried
before build submission. Unknown result size defers explicitly. Active
buckets are ordered before background buckets, oldest deferred work wins
within each priority, and the bucket key is the deterministic final
tie-break. One oversized result may pass when no other result was admitted in
the frame, guaranteeing convergence under a sub-BLAS cap.

Operation, result-byte, unknown-size, and allocation deferrals leave the prior
complete record untouched. A changed input remains fail-closed from bucket
publication until its replacement is current; force rebuild may keep using
the already-current old record while admission is deferred.

The GPU census now adds:

  admission(deferOp/deferBytes/deferUnknown/deferAlloc/query/fail/
            bytes/oversized/oversizedBytes/maxAge)

These fields accumulate until a one-shot static-bucket audit consumes the
interval, so a final audit preserves forced-low-budget evidence.

LEGACY-RIGID COMPLETE-PACKAGE REPLACEMENT
-----------------------------------------
The legacy rigid prerequisite now treats vertex buffer, index buffer, and BLAS
as one publication package. A changed upload never overwrites or individually
replaces live input buffers. It allocates both candidate buffers, creates a
candidate BLAS over those handles, uploads and submits the complete candidate,
then atomically swaps all three record handles and retires the prior package.

An unchanged force rebuild may share the immutable current buffers, but it
still creates and builds a distinct BLAS before retiring the prior handle.
Build-gate or allocation failure leaves the prior record untouched.

Route readiness now requires an exact CPU-content/upload signature in addition
to both buffers, a submitted BLAS, and exact vertex/index counts. The CPU
content signature covers the complete cached local vertex and index payload.
A retained package that no longer matches refreshed source content therefore
fails closed to the existing dynamic fallback rather than combining old GPU
geometry with new route metadata.

LEGACY-RIGID RESULT-BYTE ADMISSION
----------------------------------
The legacy rigid atomic-package provider now consumes the common deterministic
admission planner. Its independent limits are:

  r_pathTracingRigidBlasGpuBuildLimit
  r_pathTracingRigidBlasGpuResultBudgetKB

Both default to 0, meaning unlimited. The unlimited result-byte default avoids
admission-time result requirement queries and preserves existing behavior.
With a nonzero result budget, the candidate BLAS handle is queried before any
candidate buffer upload or BLAS build submission. Unknown result size defers
explicitly.

Visible records are ordered before cached background records. Within each
priority, oldest deferred work wins and mesh hash is the deterministic final
tie-break. One oversized result may enter an otherwise empty frame so a
sub-BLAS cap cannot starve a record.

Operation, result-byte, unknown-size, buffer-allocation, and BLAS-allocation
deferrals leave the prior complete package untouched. An exact retained
package remains route-ready during a diagnostic force rebuild; a stale
retained package still fails closed through the accepted content-signature
contract. Candidate buffers are not written until the complete package has
been admitted.

The one-shot rigid GPU dump adds:

  admission(deferOp/deferBytes/deferUnknown/deferAlloc/query/fail/
            bytes/oversized/oversizedBytes/maxAge)

These fields accumulate until the dump consumes the interval.
