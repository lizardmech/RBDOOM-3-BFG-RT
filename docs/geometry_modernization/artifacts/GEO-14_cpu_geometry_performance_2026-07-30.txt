GEO-14 CPU GEOMETRY PERFORMANCE FOLLOW-UP - 2026-07-30
======================================================

Purpose
-------
Investigate two post-acceptance performance reports:

1. character-heavy views were substantially slower than the retired merged
   CPU-skinned route even with GI disabled and a 640x360 PT render size;
2. `testmaps/test_gltf2_models` fell below 5 FPS despite containing only a
   small room and a modest number of model instances.

Method
------
The release renderer was rebuilt with `USE_OPTICK=ON`. Captures used CPU
instrumentation only; `r_pathTracingOptickGpuMarkers` remained zero because
the native GPU marker route is not a stable validation dependency. The
repository-local `tools/optick_capture_summary.js` reader extracted aggregate
event times directly from each `.opt` capture.

All values below cover 240 steady frames unless explicitly labelled. They are
CPU wall time inside the renderer events, not GPU timestamp results.

Skinned route result
--------------------

  capture                                      PT Build Scene   dynamic loop
  GPU route before fix (23-31-58)                 40.995 ms       4.456 ms
  merged CPU rollback (23-27-35)                  37.815 ms       9.824 ms
  GPU route after fix (23-38-02)                  37.502 ms       3.933 ms

The per-instance GPU route was not slow because it submits 12-13 BLAS
commands. Their CPU submission cost was about 0.16 ms/frame. The regression
was repeated CPU metadata construction:

  current upload route build                       2.915 ms/frame
  duplicate post-submit shadow build               2.914 ms/frame
  pending-set copy                                  0.745 ms/frame
  upload conversion                                 0.679 ms/frame

The accepted correction reuses the current-frame source-only route after BLAS
submission only when the complete live contract still validates: routable
state, instance/mesh/source checksums, source/output generations and ranges,
buffer handles, BLAS generation, and live BLAS handle. Bootstrap,
reallocation, replacement, and mismatch frames retain the post-submit rebuild.
It also removes a dead diagnostic shadow member and avoids a throwaway first
GPU-upload conversion used only to recover a signature.

The duplicate steady rebuild disappears from the post-fix capture. Build Scene
falls 3.493 ms/frame and the GPU route becomes slightly cheaper on the CPU
than the rollback while retaining the roughly 5.9 ms/frame CPU-skinning
avoidance.

GLTF rigid result
-----------------

  capture                                      PT Build Scene   dynamic loop   rigid scaffold
  before rigid-cache fix (23-39-48)               81.517 ms      33.302 ms      17.149 ms
  scaffold-only fix (23-43-03)                     64.802 ms      33.724 ms       0.830 ms
  final rigid-cache fix, 120 frames (23-48-29)     29.691 ms       5.263 ms       1.032 ms

Two independent repeated-work defects owned the GLTF CPU cost.

First, `UpdateRigidBlasGpuScaffold` converted every live rigid mesh to local
CPU vertices and indexes before checking whether its buffers, upload
signature, and BLAS were already exact. The exact check now uses the resident
range counts and cheap upload signature first. Local payload conversion occurs
only when an actual build/replacement is required.

Second, every rigid draw-surface observation rebuilt and rehashed the complete
CPU mesh cache when the transient `srfTriangles_t*` wrapper changed. A focused
60-frame capture recorded 1,140 refreshes, all attributed to that identity
condition. The stable rigid identity already contains model epoch, model
surface, GPU vertex/index identities, format, vertex/index counts, material
class, and source kind; it intentionally does not contain the transient CPU
wrapper address. The cache now invalidates on those stable content contracts,
range changes, or texture-matrix changes while still refreshing the live
wrapper pointer used by fallback/diagnostic access.

Acceptance and remaining work
-----------------------------
- Both the Optick and normal Vulkan release targets compile and link.
- The normal executable is deployed; no shader source changed and no SPIR-V
  copy is required.
- The measured CPU regressions are corrected without changing production
  route defaults or rollback CVars.
- Human visual traversal remains required for final presentation/correctness
  confirmation, especially moving rigid GLTF objects and character portal
  crossings.
- The GLTF Build Scene still costs about 29.7 ms/frame. Its largest remaining
  pieces are rigid residency, route snapshot/material construction, and TLAS
  instance snapshot/description work. These are valid candidates for a later
  cache/generation pass, but they are no longer consistent with the reported
  sub-5-FPS CPU bottleneck.
- This capture does not measure ray-traversal or shading cost. If the normal
  build remains far below the CPU-limited rate after this correction, collect
  Vulkan GPU timestamps before changing BLAS topology.

Rollback
--------
The code change is structural and has no new production gate. The existing
route rollback remains:

  r_pathTracingGeometrySkinnedTlasCompare 0
  r_pathTracingGeometrySkinnedCaptureSplit 0

Reverting this follow-up restores the old repeated CPU work but is not
required to restore legacy traversal.

PBR orb stress-map follow-up
----------------------------

`testmaps/test_pbr_orbs` remained near 14 FPS at 640x360 after the first
follow-up. An identical 240-frame Optick capture reproduced the report:

  capture / correction                         PT Build Scene   Common::Frame
  reported state (23-58-23)                       65.568 ms          n/a
  cached validation only (00-02-43)               31.193 ms          n/a
  validation + zero-copy stable reuse (00-05-22)   8.930 ms        9.720 ms

The map contains about 290k cached rigid vertices and 1.48M cached rigid
indexes. It exposed three additional linear-per-query/copy defects:

1. `RigidMeshHasCachedRouteData` was not a predicate in cost. Every call
   rescanned all cached vertices for finite positions and every cached index
   for range validity. Residency, TLAS snapshot, material collection, route
   snapshot, TLAS descriptor, and emissive paths called it independently.
   Validation now happens once when `RefreshRigidMeshCandidateCpuCache`
   creates or invalidates the cache. A stored validity bit makes later
   readiness queries constant-time without weakening the validation.
2. `PruneRigidCachesToCurrentFrame` deep-copied every live mesh record,
   including its full vertex and index vectors, into a temporary vector every
   frame even when no record expired. It now leaves a stable vector in place
   and only move-compacts records when retirement actually removes one.
3. The async route cache was deep-copied into a frame-local route build every
   stable frame. The accepted persistent route build is now the frame's
   working storage. Generation checks and upload signatures remain unchanged;
   newly accepted worker results move into that storage.

The final capture reduced the key steady events as follows:

  event                                      reported state   final
  rigid residency update                       15.288 ms      0.057 ms
  rigid route async orchestration, inclusive    14.989 ms      0.021 ms
  rigid route metadata snapshot                  6.326 ms      0.010 ms
  rigid TLAS snapshot                            6.144 ms      0.021 ms
  rigid route material IDs                       6.136 ms      0.011 ms
  rigid TLAS instance descriptors                6.161 ms      0.027 ms

The final total CPU `Common::Frame` average is 9.720 ms (about a 103 FPS CPU
ceiling) under the same low-resolution, GI-off, route-1 configuration. This
does not substitute for Vulkan GPU timestamps, but it proves the reported
14-FPS result was CPU-limited before these corrections and that geometry
scene construction is no longer the limiter in this map.

Moving-camera persistent-pool follow-up
---------------------------------------

The first moving-camera capture showed that the steady-frame fix did not
cover portal/membership transitions. A route generation change still rebuilt
the complete 290k-vertex / 1.48M-index pool:

  capture / correction                         Common::Frame   sync full builds
  moving baseline (00-28-36)                     13.621 ms       16 / 600
  persistent geometry pool (00-37-45)             10.427 ms        0 / 600

Each baseline full build averaged 107.946 ms. The replacement follows the
static-geometry split used by the NVIDIA RTXPT and RTXDI samples:

- immutable mesh geometry is appended to persistent pooled storage once;
- cached geometry ranges carry mesh/upload identity and pooled offsets;
- current membership, transforms, history flags, and material overrides are
  rebuilt in the small instance array;
- material-table changes remap the triangle material-index side buffer without
  recopying vertex or index payloads;
- meshes retained by the 900-frame mesh window remain reusable even though
  entity-feed instance residency retains its separate two-frame safety cap.

During the accepted 600-frame traversal, 27 instance-list rebuilds consumed
0.338 ms total (0.013 ms average each). Ten geometry-generation transitions
were satisfied from already resident ranges. There were no full route builds,
payload snapshots, or asynchronous full-payload queues.

The user reported that movement was substantially improved. A few cold
first-exposure hitches remained and disappeared after the scene had been on
camera. A capture starting at map admission attributed those cold costs to
draw-surface capture (up to 253.731 ms), entity-feed candidate admission (up
to 80.996 ms), and initial rigid BLAS package creation (up to 90.700 ms).
Those are distinct from the corrected recurring pool repack and are deferred
as a separate cold-admission optimization.

Matched Fatzombie view follow-up
--------------------------------

Two saves captured the same location with only the camera direction changed:

  doom3_2   worst character-heavy view
  doom3_3   adjacent highest-FPS view

Both captures used 640x360 PT output, GI disabled, CPU-only Optick markers,
and 360 steady frames. The initial matched comparison proved that the
reported slowdown was CPU scene construction, not DI/GI or ray resolution:

  event                                      doom3_2 worst   doom3_3 wall   delta
  Common::Frame                                  42.134 ms      19.183 ms  22.951 ms
  PT Build Scene                                 40.761 ms      17.823 ms  22.938 ms
  PT Capture Doom Surfaces                       11.521 ms       5.009 ms   6.513 ms
  PT Skinned Route Current Upload Build           4.743 ms       0.000 ms   4.743 ms
  PT Emissive Inventory                           5.153 ms       3.136 ms   2.016 ms
  PT Skinned GPU Scaffold                         1.396 ms       0.002 ms   1.393 ms
  PT Register Material Metadata                   1.865 ms       0.531 ms   1.334 ms
  PT Skinned Route Pending Set Copy               1.076 ms       0.000 ms   1.076 ms
  PT Skinned Route Upload Conversion              0.979 ms       0.002 ms   0.977 ms

The worst view contains 25 source-only skinned route surfaces with 68,172
indexes. Their materials are non-emissive, including the spawned Fatzombies.
Four repeated-work defects were corrected:

1. Production route construction calculated canonical and emissive 64-bit
   identities for every triangle, although hit shaders do not consume either
   field. Canonical identities are now generated only for explicit
   validation. Emissive identities remain generated for genuinely eligible
   skinned emissive materials and for validation.
2. The skinned emissive path copied the complete current/previous skinned
   vertex arrays, decoded canonical placeholder vertices, and constructed an
   audit-triangle record for every non-emissive character triangle before
   filtering by material. Production now prefilters route metadata and lazily
   creates those arrays only when an eligible emissive triangle exists.
   Forced emissive validation retains the complete previous behavior.
3. The current route upload was converted to GPU layout a second time solely
   to derive the pending-set signature, then deep-copied into unchanged
   pending and accepted route sets every frame. The already-computed upload
   signature is now reused, and unchanged route sets remain in place.
4. Material metadata performed another complete validation walk of the visible
   draw-surface array after capture had already produced its unique visible
   material IDs. Hydration now combines that captured set with persistent
   static/rigid IDs. Per-frame classifier setup and the dynamic texture-handle
   refresh subset remain active; material-table ordering is unchanged.

The same worst-view capture after each correction measured:

  event                                      initial   identities   emissive   route reuse
  PT Build Scene                              40.761 ms   37.530 ms  34.675 ms   33.925 ms
  current upload route build                   4.743 ms    0.706 ms   0.709 ms    0.710 ms
  emissive inventory                           5.153 ms    5.315 ms   3.471 ms    3.500 ms
  pending-set copy/signature                    1.076 ms    1.073 ms   1.068 ms    0.002 ms
  accepted-set copy                            0.067 ms    0.071 ms   0.068 ms    0.001 ms

The material-hydration follow-up reduced `PT Register Material Metadata` from
1.893 ms to 0.001 ms and the final worst-view `PT Build Scene` to 31.782 ms.
That is 8.979 ms, or 22.0 percent, below the initial 40.761 ms.

The final exact-build matched captures measured:

  event                                      doom3_2 worst   doom3_3 wall   delta
  Common::Frame                                  33.170 ms      19.603 ms  13.567 ms
  PT Build Scene                                 31.782 ms      18.239 ms  13.543 ms

The character-view gap therefore fell from 22.938 ms to 13.543 ms, removing
9.395 ms or 41.0 percent of the view-dependent CPU regression.

The remaining worst-versus-wall difference is about 13.5 ms. Its largest
measured pieces are view-dependent draw-surface capture/dynamic-material
records, the skinned GPU scaffold, and the still-required one-time-per-frame
GPU route conversion. They require broader caching or capture-contract changes
and are not conflated with the four proven redundant operations above.
