GEO-06 - pooled mesh ingestion entry audit
============================================
Status: entry audit complete; callback-MD5 registry proof passed; checked
allocation and immutable CPU source-registry slices complete.
Date: 2026-07-24.

SCOPE
-----
This is the required current-code audit before GEO-06 allocation or routing
changes. It treats the ticket and decision register as contracts, not the older
proposal documents. No pooled buffer or live-route code is implemented here.

CURRENT RIGID ROUTE
-------------------
RtSmokeGeometryUniverse::RigidMeshCandidateRecord currently combines four
different ownership domains:

  source observation: const srfTriangles_t* tri and sourceRange;
  cached CPU payload: cachedLocalVertices/cachedLocalIndexes;
  GPU storage: one rigidVertexBuffer and rigidIndexBuffer per mesh candidate;
  acceleration: one rigidBlas plus its desc/build state per mesh candidate.

The route already shares a candidate BLAS among its eligible rigid instances.
Its scalability problem is storage ownership: every unique candidate owns
separate vertex/index buffers, while frame route buffers merge copies and carry
uint32 vertexOffset/indexOffset/triangleOffset per instance.

PathTraceSmokeVertex is the legacy interleaved rendered layout:

  position, normal, texCoord, color, color2, tangent, bitangent.

It is full fidelity, but it is not the new registry ABI. D13 requires raw
float3 positions to be split from full-fidelity attributes immediately.
Therefore GEO-06 must not name an interleaved PathTraceSmokeVertex allocation
the canonical pool and defer the split.

OFFSET AND BLAS AUDIT
---------------------
NVRHI GeometryTriangles already exposes uint64 vertexOffset and indexOffset.
The Vulkan backend adds each offset to the corresponding buffer device address
and uses vertexCount - 1 as maxVertex.

The local wrapper is not ready:

  InitSmokeTriangleGeometry accepts only an int indexOffset;
  it hard-codes vertexOffset=0;
  CreateSmokeBlas accepts counts but no byte ranges;
  the wrapper assumes sizeof(PathTraceSmokeVertex) vertex stride.

The canonical wrapper must accept checked byte offsets and explicit position
stride/count. It must reject misalignment, overflow, out-of-buffer ranges and
uint32 count narrowing before creating an acceleration structure.

ACCEPTED FIRST STORAGE ABI
--------------------------
The first pool slice must keep these allocations logically separate:

  position bytes
    raw full-precision float3 positions used by BLAS;

  attribute bytes
    full-fidelity normal, UV, color/color2, tangent and bitangent data;

  index bytes
    uint32 local vertex indices;

  triangle bytes
    material ID, material-table binding/revision, triangle class/flags and
    any emissive-local metadata required by current consumers.

Each immutable mesh source record must contain:

  canonical MeshKey;
  source content generation/revision;
  source checksum plus full-key equality;
  buffer storage generation;
  uint64 byte offset, byte size and alignment for every allocation;
  vertex/index/triangle counts;
  explicit residency/upload/BLAS states;
  last-use/retirement information sufficient to keep in-flight generations
  alive during pool growth.

Canonical identity must not contain storage offsets, material state, AS handles
or frame route indices. Shader uint32 values may be produced only by checked
page-relative narrowing.

IMPLEMENTATION ORDER AFTER THE MD5 GATE
---------------------------------------
1. Add pure checked uint64 allocation/range helpers and deterministic CPU tests
   for alignment, addition/multiplication overflow, near-4-GiB offsets, page
   narrowing and growth-generation preservation.
2. Add observation-only CPU source records keyed by canonical MeshKey. Copy
   immutable source payload on first discovery/source revision; do not retain a
   frame-temporary srfTriangles_t pointer as durable ownership.
3. Add separate position/attribute/index/triangle growable GPU pools and
   storage-generation retirement. Keep the live rigid route unchanged.
4. Count first upload bytes, revision uploads, steady-state upload bytes,
   source reuse, retained bytes, rejected ranges and retired generations.
5. Extend the BLAS descriptor wrapper with uint64 byte offsets and validate a
   Vulkan non-zero-position/non-zero-index-offset micro-test, including first
   and last primitive material/attribute lookup.
6. Add same-content shadow comparison against BuildRigidLocalMeshData for
   counts, checksums, material ranges and representative decoded endpoints.
7. Adapt the established rigid route behind a new default-off compare gate.
   One eligible immutable mesh owns one pooled BLAS; TLAS instances retain
   independent transforms and InstanceKeys.
8. Compare old/new rigid geometry, material, transform, motion, emissive and
   lifecycle tuples. Enumerate every mismatch; do not silently fall back.
9. Validate repeated rigid props as positive sharing controls and repeated
   zombies/Fatzombie as negative routing controls. Skinned source records may
   share immutable data, but no live skinned output or BLAS may enter the rigid
   route.
10. Validate removal/re-add, map restart and pool growth while old buffer
    generations are in flight, then collect identical-content upload/memory/
    BLAS/TLAS measurements.

STEP 1 CHECKED POOL PLANNER (2026-07-24)
----------------------------------------
Implemented:

  neo/renderer/NVRHI/PathTraceGeometryPoolPlan.h/.cpp
  neo/tests/pathtrace_geometry_pool_harness.cpp

The planner is pure CPU code with no renderer object, NVRHI resource, pointer,
upload or live-route input. It defines:

  checked elementCount * elementStride byte sizing;
  aligned append allocation using uint64 byte offsets/sizes;
  failure-atomic capacity/overflow rejection;
  bounded geometric growth with a monotonic storage generation;
  explicit old/new capacity, copy bytes and generation in the growth plan;
  range rebasing only when the entire source range belongs to the previous
  generation and lies inside the copied payload;
  stable named results for every rejection.

The deterministic PathTraceGeometryPoolHarness covers:

  aligned append and padding;
  capacity failure without state mutation;
  empty size, zero alignment and zero element stride;
  element counts above UINT32_MAX;
  multiplication/alignment/end overflow;
  absolute allocation at the 4 GiB boundary;
  checked page-base subtraction before shader uint32 narrowing;
  no-growth generation preservation;
  1 KiB -> 8 KiB bounded growth and generation 7 -> 8;
  preservation of copied range offset/size across growth;
  wrong-generation and not-fully-copied range rejection;
  maximum-capacity and generation-overflow rejection.

STEP 2 IMMUTABLE CPU SOURCE REGISTRY (2026-07-24)
-------------------------------------------------
Implemented:

  neo/renderer/NVRHI/PathTraceGeometrySourceRegistry.h/.cpp
  neo/tests/pathtrace_geometry_source_registry_harness.cpp

The source registry is still pure CPU code with no live lifecycle call site,
renderer pointer, NVRHI resource, upload, BLAS or route mutation. It owns four
separate value streams:

  raw float3 positions;
  full-fidelity decoded normal, UV, color/color2, tangent, bitangent and
    bitangent-sign attributes;
  uint32 local indexes;
  source material slot, triangle class/flags and geometry-local emissive index.

The registry accepts only valid RegisteredRenderModel + Rigid canonical mesh
keys in this slice. Static world data is deferred to the static-bucket ticket.
SkinnedBindSource and Skinned observations are named negative controls so an
animated MD5 snapshot cannot be mistaken for immutable rigid source data.

The initial proposal put resolved material ID and material-table binding/
revision in the immutable triangle stream. That is incompatible with D17:
skins and per-instance material overrides are binding state, not MeshKey-owned
source content. The corrected source ABI retains a stable source material slot.
The later instance/route binding record resolves that slot to a material-table
ID and revision. This prevents one instance override from revising or replacing
a source record shared by other instances.

Observe behavior is explicit:

  first non-zero source revision plus a complete payload
    validates counts/topology/local index ranges, computes one source checksum,
    deep-copies all four streams and returns Added;

  the same canonical key and source revision
    returns Reused without accepting, hashing or copying a payload;

  a larger source revision plus a complete valid payload
    builds a replacement, updates checksum/retained bytes and returns Revised;

  a stale/zero revision, missing payload, count mismatch, non-triangle
    topology, out-of-range index or ineligible source class
    returns a stable named rejection without publishing a partial record.

The deterministic PathTraceGeometrySourceRegistryHarness covers:

  separate position and attribute ownership;
  mutation of caller arrays after ingestion;
  exact retained/copied-byte accounting;
  steady same-revision reuse with no second payload copy;
  content-revision replacement and checksum change;
  stale-revision failure atomicity;
  static/skinned negative controls;
  zero revision and missing first-discovery payload;
  stream-count, topology and local-index validation;
  checksum sensitivity to indexes, source material slots and bitangent sign.
