INTERPRETATION
--------------
The recurring 0.9-1.8 second stalls belong to the screen-space particle
composite path. CPU alpha sorting is not required for the failure. The
particle-lighting compute path is not required for the failure. Scene-build
logging remained in the normal low-tens-of-milliseconds range, while the next
com_speeds row attributes the long stall to bk, so the CPU geometry capture/
scene-build path does not explain it.

The most suspicious unmeasured operation is per-batch graphics binding-set
creation in ExecutePathTraceParticleComposite, but the A/B does not prove that
as the cause. Buffer growth, texture/batch churn, and later Vulkan submission
or descriptor reclamation remain possible.

NEW BOUNDED DIAGNOSTIC
----------------------
  r_pathTracingParticleDump 1
    One composite frame plus up to 16 batch records.

  r_pathTracingParticleDump 2
    Trace exactly 240 attempted composite frames, one concise line per frame,
    then auto-disable.

The trace reports frame-aligned capture/vector counts, upload bytes, buffer
handle changes, lighting state, descriptor binding-set create count/failures/
CPU time, draw count, and setup/sort/buffer/upload-lighting/draw-record CPU
phase timing. Use mode 2 together with com_speeds 1 at the malfunctioning
monster. Do not apply a descriptor-cache fix unless those aligned records
distinguish descriptor creation/reclamation from buffer or batch churn.
