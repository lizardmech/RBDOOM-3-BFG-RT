Clean RTXDI DI Glass Shading Notes
==================================

Purpose
-------

This note records the current design direction for turning the clean RTXDI DI
glass material-feature proof into a basic usable glass shader.

The main architectural lesson from the early experiments is that usable glass
does not start with Fresnel color math. It starts with primary surface
replacement (PSR): resolve the surface seen through the glass first, let the
normal clean RTXDI DI path shade that replacement surface, then add the glass
surface response afterward. Every other glass function is secondary until that
contract works.

The near-term goal is not full RTX Remix parity. It is a narrow, testable,
clean-DI view 16 glass slice that:

    uses the modular material-feature pass path
    does not add glass branches to unrelated DI/GI math
    keeps unsupported material kinds fail-closed
    replaces glass primary pixels with resolved behind-glass surfaces before DI
    applies glass attenuation/reflection only after the behind surface is shaded
    produces a primary-view effect, not only a debug color
    can be replaced or expanded by later shader implementations

Useful Remix Shape
------------------

The useful first slice is thin-walled translucent glass.

Remix translucent materials are organized around:

    material parameters:
        base reflectivity or IOR-derived F0
        refractive index
        transmittance color
        thickness or measurement distance
        optional diffuse layer
        optional emissive layer

    interaction state:
        shading normal
        base reflectivity
        refractive index
        transmittance color
        diffuse color and opacity
        thickness or measurement distance
        flags

    lobes:
        specular reflection
        specular transmission

For thin-walled glass, negative thickness marks a thin surface. Transmission
does not need to enter nested medium tracking for the first pass. The main
effect is a specular/transmission split plus Beer-Lambert attenuation through a
thin-surface distance.

The useful Remix shape is not just the translucent material formula. The
important part is that transmission participates in surface resolution. For
transparent pixels, Remix-style rendering can replace the primary surface seen
by the lighting/denoising pipeline with the surface behind the glass, while
carrying glass attenuation and surface contribution as separate data for the
late resolve.

For rbdoom, that means the first credible clean-DI glass slice is:

    pre-DI PSR phase:
        identify supported glass pixels from the original primary surface
        trace or otherwise resolve the behind-glass primary surface
        write a complete replacement primary-surface record for DI
        store the original glass overlay data separately

    normal clean DI phase:
        shade the replacement surface using existing clean RTXDI DI code
        do not add glass-specific branches to DI/GI reservoir math

    late glass overlay phase:
        read the saved glass overlay data, not the replaced primary record
        apply thin-glass throughput, Fresnel/reflection, tint, and debug output
        write beauty/RR input color through the material-feature output path

Until the PSR handoff works, Fresnel, Beer-Lambert attenuation, chromatic
offsets, roughness, normal maps, and tint controls are only local surface
effects. They cannot make black legacy glass transparent and they cannot show
properly shaded objects behind the pane.

The first rbdoom slice should still avoid Remix's full medium tracker,
multi-bounce resolver, and complete DLSS/RR guide replacement. It should not
avoid PSR itself. PSR is the minimum architecture required for usable glass in
the clean RTXDI DI primary view.


Do Not Pull In Yet
------------------

Do not bring these into the first glass shader:

    Remix polymorphic material table layout
    Remix GBuffer material serialization
    thick medium enter/exit tracking
    nested translucent media
    animated water normal layering
    diffuse translucent layer
    decals applied onto translucent material
    Slang build participation
    direct-light or GI transmissive reservoir behavior

Those are separate contracts. Pulling them in early would make the clean-DI
feature route depend on unrelated renderer structure.

Do bring in the rbdoom-owned PSR contract. The local version can be smaller
than Remix's resolver, but it must still keep the same ownership split:

    replacement primary surface for clean DI
    saved glass overlay/source record for late glass shading
    explicit transmission/throughput payload
    debug views proving each phase independently


Initial rbdoom Glass Contract
-----------------------------

Start with a rbdoom-owned PSR handoff, then keep glass math small and local.
The HLSL helpers are useful only after the pass has a real behind-glass surface
to shade.

Required PSR contract:

    the original glass primary surface remains available after replacement
    the replacement primary record is fully packed, not a hybrid glass/background
        record
    material id, material index, material flags, alpha cutoff, surface class,
        emissive texture index, instance id, primitive id, previous position,
        normals, roughness, albedo, specular, and emissive fields all match the
        resolved behind-glass hit
    the late glass pass does not rediscover glass by rereading the replaced
        `PrimarySurfaceHistoryCurrent` record
    unsupported or missed transmission leaves the original glass path
        fail-closed and visible in debug

Suggested helper set after PSR is proven:

    GlassIorToF0(incidentIor, transmittedIor)
    GlassSchlickFresnel(f0, viewDotNormal)
    GlassSchlickFresnelTir(f0, relativeIor, viewDotNormal)
    GlassTransmittanceToAttenuation(transmittanceColor, measurementDistance)
    GlassBeerLambert(attenuationCoefficient, distance)
    GlassThinAttenuationDistance(thickness, normal, direction)
    GlassThinTransmissionThroughput(outsideFresnel, insideFresnel, attenuation)
    GlassThinReflectionThroughput(outsideFresnel, insideFresnel, attenuation)

Keep the first shader dirac-only:

    no roughness
    no GGX/VNDF
    no diffuse transmission
    no multibounce path recursion beyond the existing clean-DI route

Good starter defaults:

    incident IOR: 1.0
    glass IOR: 1.45 to 1.52
    transmittance color: runtime parameter, default near white
    thin thickness: runtime parameter, small positive scalar
    fallback F0: derived from IOR unless an explicit sidecar value exists


Parameter Source
----------------

Use `pathtrace_clean_rtxdi_di_glass_params.hlsli` as the shader-facing parameter
adapter. Runtime parameter lanes are defaults and global proof controls, not the
final material ABI.

Near-term mapping:

    featureParams0.xyz = transmittance color
    featureParams0.w   = thin thickness
    featureParams1.x   = IOR
    featureParams1.y   = strength
    featureParams1.z   = compose reflection boost
    featureParams1.w   = compose transmission floor
    material-feature sidecar/surface data may override transmittance tint per
        material when a valid glass feature record is present
    `PathTraceMaterialFeatureParameters` stores one parameter row per material
        table entry, currently keyed by `parameterRecordIndex`
    object-glass and portal-window fallback materials have separate initial
        parameter defaults to prove the table can carry more than one glass
        shader setting

After proof:

    add a glass parameter sidecar keyed by material index or feature
    move transmittance color, IOR/F0, thickness, and optional roughness there
    leave runtime constants for global debug/control values only


Output Contract
---------------

The existing transmission producer proof writes a sentinel transmission UAV.
For PSR, one texture is not enough to describe the whole contract. The output
must distinguish:

    replacement status:
        no glass
        supported glass but transmission miss
        supported glass and replacement succeeded

    glass overlay payload:
        original glass material/surface identity or a compact saved record
        thin-glass throughput
        overlay weight/coverage
        optional debug classification

Recommended first payload:

    rgb = thin-glass transmission/attenuation color
    a   = PSR/replacement state or glass coverage, but document which one

The output should be produced only when:

    clean RTXDI DI view 16 is active
    the feature pass is enabled
    the surface has PATH_TRANSMISSION material capability
    the material kind is translucent glass
    the sidecar ABI/version check passes

Unsupported materials should write a dark sentinel only in debug mode, not
beauty output.


Primary-View Consume
--------------------

The glass shader is not useful until clean-DI consumes the PSR output in the
primary view. Keep this consume step explicit and narrow.

Correct first compose shape:

    before clean-DI:
        save glass overlay data for supported glass pixels
        replace the primary surface with the resolved behind-glass surface

    after clean-DI primary lighting is available:
        if PSR did not replace the pixel, leave primary color unchanged or show
            a debug/fail-closed glass color
        if PSR replaced the pixel, treat current primary color as shaded
            behind-glass radiance
        apply a controlled overlay:
            output = behindColor * transmissionRgb + reflectedGlassTerm

This is still a simple thin-glass approximation, but it proves the right
architecture: shaded scene first, glass surface second. A post-DI tint pass over
the already-rendered glass surface is not enough.

Current implementation checkpoint:

    `r_pathTracingCleanRtxdiDiTransmissionProducer 1` writes the thin-glass
        transmission payload to `PathTraceCleanRtxdiDiTransmissionOutput`
    `r_pathTracingCleanRtxdiDiTransmissionCompose 1` enables the glass
        material-feature pass to read that sidecar as `t87` after clean DI and
        write the final output/RR input color. The current compose is still
        neutral for visual parity; it exists to put final glass ownership in
        the glass pass rather than the transmission producer.
    `r_pathTracingCleanRtxdiDiTransmissionDebugView 1` still overrides compose
        and writes the payload/debug visualization instead

The removed screen-space compose behaviors were scaffolding only. They should
not be restored as the target transparency architecture. If a transmission path
only shades one hit manually, samples a screen-space source pixel, or attenuates
the current glass color, it is a fallback/debug approximation and not the PSR
contract.

Do not use this as a direct-light or GI transmissive reservoir contract. DI/GI
should continue to fail closed for glass until a later task explicitly opens
that consumer.


PSR Failure Modes To Avoid
--------------------------

The current code reviews identified several ways a PSR attempt can look
directionally correct but still fail:

    destructive glass lookup:
        replacing `PrimarySurfaceHistoryCurrent` and then asking the late glass
        pass to rediscover glass from that same record removes the glass
        metadata the pass needs

    hybrid primary records:
        updating position/normals/material index but leaving material id,
        flags, alpha cutoff, surface class, emissive texture index, or previous
        position from the original glass record creates impossible surfaces for
        clean DI to shade

    phase reuse without ownership:
        using the same transmission material-feature pass for pre-DI PSR and
        post-DI compose was only a temporary bridge. Transmission now owns PSR
        sidecar generation; glass owns the post-DI output-color compose.

    output priority inversion:
        transmission should produce replacement/throughput data; the final
        visible glass overlay should own beauty composition once PSR succeeds

    one-hit reshading:
        tracing through glass and inventing albedo or analytic lighting in the
        transmission shader does not match the scene behind the glass. The
        replacement surface must go through the normal clean DI shading path.


DLSS/RR Normal Guide Rule
-------------------------

RTX Remix treats refractive glass normals specially for DLSS Ray
Reconstruction guide data. The glass surface normal itself is not exported as
the normal guide for the refracted view. Instead, the surface seen behind the
glass is the meaningful guide source, with its normal distorted by the glass
path when that resolver exists.

Carry that rule into rbdoom when glass reaches RR guide integration:

    do not write the glass surface normal into `PathTraceRRGuideNormalRoughness`
        merely because the primary ray hit glass
    do not let the first thin-glass tint prototype overwrite existing opaque
        guide normals behind the glass
    if a future refractive resolver traces through glass, export the resolved
        seen-through surface normal/roughness, transformed consistently with
        the refracted path
    if the seen-through surface is unavailable, prefer fail-closed or preserve
        the previous valid guide over inventing a glass-normal guide

This is separate from the first beauty consume step. The first glass slice may
leave RR guide generation unchanged, but it must not claim RR correctness until
the refractive guide-normal contract is implemented and debugged.

Direct Live RR Tuple Write Failure
----------------------------------

2026-07-02 validation found that writing a behind-glass RR tuple directly from
the clean-DI glass material-feature shader into the live Streamline guide
resources is unsafe. The attempted slice wrote the refracted source surface into
`PathTraceRRGuideNormalRoughness`, `PathTraceRRGuideDepth`,
`PathTraceRRGuideResetMask`, `PathTraceRRMotionVectors`, and
`PathTraceRRGuidePosition` from the glass feature pass. Runtime symptom:
clean RTXDI DI view 16 became a purple primary output; enabling glass plus
DLSSRR showed only emissive and glass-like surfaces, not the full primary view.
Rolling the tuple experiment back restored normal rendering.

Treat this as a contract rule, not as a transient bug:

    the glass material-feature shader may adjust RR input color/specular guide
        only through the already validated color path
    it must not overwrite live Streamline normal/depth/motion/position guides
        from a shader-local screen-space source pixel
    a future RR glass guide implementation needs a separate resolved-guide
        candidate contract, with ownership, barriers, debug views, and a
        compositor/validator pass that updates normal, depth, motion, position,
        and reset state as one coherent tuple
    until that pass exists, keep live RR guide normal/depth/motion replacement
        disabled and leave DLSSRR glass guide parity as a non-goal

DLSS/RR Specular Channel Rule
-----------------------------

Shipping DLSS Ray Reconstruction integrations commonly separate glossy
reflected radiance into the specular reconstruction path instead of leaving RR
with only base specular material metadata. rbdoom currently has guide resources
such as `PathTraceRRGuideSpecularAlbedo`, but a basic material F0/specular guide
is not the same thing as giving RR the glossy reflected ray contribution that it
should reconstruct.

Carry this into glass and future glossy work:

    do not treat `PathTraceRRGuideSpecularAlbedo` alone as proof that RR has the
        reflected-ray/specular signal it needs
    keep diffuse/base lighting and glossy reflected radiance separable before
        RR evaluate
    when glass or glossy reflections produce secondary reflected radiance,
        route that contribution into the specular RR channel or equivalent
        split input, not only into a combined beauty color
    keep the base specular/F0 guide as material metadata, not as a replacement
        for reflected glossy radiance
    add a debug view or dump that proves reflected-ray energy is present in the
        specular RR input before claiming RR parity

For the first thin-glass tint prototype, it is acceptable to leave this as a
documented non-goal. Once glass has actual reflection/refraction rays, RR
integration should be revisited so reflected and refracted components are not
collapsed into the wrong reconstruction channel.


Validation Route
----------------

Each step must be observable in clean-DI view 16.

Minimum checks:

    baseline:
        glass feature disabled
        no visual change from current clean RTXDI DI view 16

    debug:
        glass debug view shows known glass candidates
        glass debug view shows sidecar status after PSR replacement:
            green = late glass pass saw PSR payload
            yellow = glass was detected but continuation miss/pending
        unsupported/translucent non-glass remains visibly fail-closed in debug

    beauty:
        PSR replacement owns the resolved behind-glass surface
        normal clean DI owns lighting/material shading for that surface
        late glass compose only applies sidecar transmission throughput
        sidecar RGB stores transmission; sidecar alpha is 1.0 + reflection energy
            for valid PSR payloads, while 0.25 remains the detected-but-missed sentinel
        sidecar encode/decode must use pathtrace_clean_rtxdi_di_transmission_sidecar.hlsli
        late compose applies the default glass reflection boost and transmission floor
        runtime tuning uses r_pathTracingCleanRtxdiDiGlassReflectionBoost and
            r_pathTracingCleanRtxdiDiGlassTransmissionFloor

    producer:
        PSR detects supported glass pixels before DI
        transmission sidecar changes from sentinel/debug state to real payload
        opaque surfaces do not write a contribution

    PSR:
        replacement primary record shows the behind-glass material and surface,
            not stale glass flags mixed with behind-glass position
        late glass debug can still identify the original glass overlay after
            the primary record has been replaced
        disabling PSR returns to the old glass/fail-closed path

    consume:
        primary view changes only on glass-like materials
        disabling the compose or producer returns to baseline
        unsupported materials never fall back to old diffuse/albedo lighting

    logging:
        pipeline init prints feature id
        descriptor validation has no failures
        validation string names the glass payload and consume route


Suggested Implementation Order
------------------------------

1. Define the PSR sidecar/overlay contract.

    Decide where the original glass surface data and throughput live after
    `PrimarySurfaceHistoryCurrent` is replaced. This can be a compact texture or
    structured payload, but it must be separate from the replaced primary
    record. Document the resource slots and debug states.

2. Add the pre-DI PSR phase.

    For supported glass pixels, trace/resolve the behind-glass hit and write a
    complete primary-surface replacement record. Do not leave stale glass fields
    in the replacement. On miss, mark the overlay payload as failed and leave a
    debug-visible state.

3. Wire the normal clean DI path to shade the replacement.

    The DI/GI code should not learn glass internals. It should see an ordinary
    primary surface after PSR. Validate with debug views that the behind-glass
    surface receives normal clean DI lighting, not hand-shaded albedo.

4. Add the late glass overlay pass.

    Consume the saved glass overlay payload after clean DI. Apply thin-glass
    attenuation/reflection over the shaded replacement color. The pass must not
    depend on rereading glass from the replaced primary record.

5. Add `pathtrace_clean_rtxdi_di_glass_math.hlsli`.

    Include only the small thin-glass helpers. Keep the file rbdoom-owned and
    note Remix as the reference in the header comment if formulas are derived
    from that audit.

6. Replace the glass proof color with thin-glass payload generation.

    Use runtime constants for transmittance color, IOR, and thickness. Write
    RGB attenuation and alpha/weight into the transmission output. Preserve
    debug output as a separate view, not the beauty payload.

7. Move glass parameters into a sidecar.

    Add a compact parameter record once the output and consume path are proven.
    Keep ABI version checks and fail closed if the parameter record is absent
    or mismatched.

8. Only after PSR plus late overlay is stable, consider expansion.

    Possible expansions:
        rough glass lobe
        true reflection/transmission split
        path-integrator transmission bounce
        RR guide interaction
        thick-medium attenuation
        DI/GI transmissive contracts


Acceptance
----------

The basic glass shader is acceptable when:

    supported glass pixels can be replaced by shaded behind-glass primary
        surfaces in clean RTXDI DI view 16
    the final glass look is added after the behind surface has been shaded
    it affects clean RTXDI DI primary view 16 through the material-feature path
    the effect is gated by glass material capability and feature cvars
    disabling the feature restores baseline
    unsupported materials fail closed
    no unrelated legacy/experimental render path is touched
    no DI/GI math receives glass-specific branches
    shader build/deploy proof names the active glass blob
    runtime validation proves debug, PSR producer, and late overlay behavior
